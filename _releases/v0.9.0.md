## ✨ New Features

### Skills' links to other files now keep working after install

- Before, an installed skill lost the files it linked to outside its own folder, such as a sibling skill it compares itself with or a shared checklist, so those links were dead in every agent's skills folder. Sync and update now keep a copy of every file a skill's links reach, from the revision the project installs, and installed skills now link to those copies, to the installed copy of a linked skill, or to the project's fork of it. (#181)
- When an installed skill links to a skill you exclude, its files are now kept for reading only, never installed, and sync warns you which skill links to it. (#181)
- Learn more in [Links](https://trailguide.fabricahq.com/reference/skill-format/#links) and [When a skill links to a skill you exclude](https://trailguide.fabricahq.com/guides/install-skills/#when-a-skill-links-to-a-skill-you-exclude).

### Projects keep teammates on a recent enough trailguide

- Before, a teammate on an older trailguide version could read the same configuration and lockfile and quietly write different output. `.trailguide/config.yaml` now records `minTrailguideVersion`: init writes it, `project update` raises it to the version that ran the update and asks you to confirm, and an older release now fails with `upgrade-required` instead of writing anything. Releases before v0.9.0 reject the field as unknown. Learn more in [Minimum Trail Guide version](https://trailguide.fabricahq.com/reference/configuration/#minimum-trail-guide-version). (#183)

```yaml
minTrailguideVersion: 0.9.0
```

## ⛓️‍💥 Breaking Changes

Because Trail Guide is in active initial development, we're not including upgrade instructions.

### Libraries keep each skill in a folder for its origin

Library authors are affected. A library now keeps every skill it authors in a folder named for its origin: its own skills in `skills/<library.name>/`, and forks in `skills/<source>/`. Its manifest now requires `library.name` and `library.schemaVersion: 2`, and Trail Guide refuses libraries on schema version 1. Projects' own skills move to `.trailguide/skills/local/`. Skill IDs stay `skills/<name>`, so projects that use a library change nothing in their configuration. Library check, sync, and build name the folder each misplaced skill belongs in. Learn more in [Library layout](https://trailguide.fabricahq.com/reference/library-schema/#library-layout). (#184)

### The `AGENTS.md` marker no longer records a version

A new Skills and Rules section in `AGENTS.md` now begins with a marker that holds only its digest, such as `<!-- trailguide:begin sha256:… -->`, so a teammate on another release no longer rewrites the section or fails `check` because of it. Markers that earlier releases wrote keep their version. (#183)

### Broken links in skills now fail

Sync, update, build, and check now fail, without writing anything, when an installed skill or one of the project's own skills links to a file that's missing, a folder, a rule file, or a path outside its repository, and `trailguide library check` and `trailguide library release` report the same links to library authors. Each error names the file, the link, and the chain of links that reached it, and `--json` errors include a `reference` object. (#181)

### Projects need one sync to keep their skills' linked files

A project synced with an older Trail Guide has no copies of the files its skills link to outside their own folders, so build and check can fail with `reference-not-retained` until you run `trailguide project sync` once. Sync takes the files from the revisions your lockfile records without moving any source. (#181)

### Library license files can't sit under `_repository/`

Library manifests can no longer declare a license or notice file under `_repository/`, which now holds the files skills link to from outside a library's `.trailguide/` folder. (#181)
