A **library** is a repository whose manifest publishes its authored **rule groups**, **skills**, and shared assets for other repositories. Libraries are useful because projects take from them: you write rules and skills once and reuse them in every codebase that needs them. A **project** is a repository that takes rules and skills for its own work. A repository can be both.

Libraries live in Git repositories. This page covers what makes a repository a library. For the rule and rule group files inside it, see [Rule and rule group format](/reference/rule-format/); for skill folders, see [Skill format](/reference/skill-format/). For how each rule and skill is versioned, see [Rule and skill versions](/reference/rule-versions/).

## Library layout

A library uses the same Trail Guide directory as every other repository. The tree below shows a library repository named **`engineering-rules/`**; the name is an example. A project that uses it stores a vendor snapshot of this content under `.trailguide/vendor/<source-name>/`; see [Project files](/reference/files/).

A library publishes exactly its **authored content**:

- **Rule groups** under `rules/techs/` and `rules/practices/`, each with its rule group metadata and rules.
- **Skills** under `skills/`, one folder per skill.
- **Library-wide files**: the manifest in `config.yaml`, rule group metadata, shared files in `assets/`, and the declared license and notice files.

`vendor/` and `generated/` are the library's own project files, for the sources it takes from and the guidance its own agents read. Projects never take them from the library.

Trail Guide discovers rule groups only under `rules/techs/` and `rules/practices/`, and skills only as `skills/<name>/SKILL.md`. A rule's ID is its path in `rules/` without `.md`, such as `practices/testing/verify-retry-limits`, and a skill's ID is `skills/<name>`.
Within a rule group, Markdown files outside reserved asset directories are rules. The `README.md` at the rule group's root and declared license and notice files, which can't use a rule's path, are exempt. Rule group READMEs are authoring documentation, not generated rule guidance.
[Change notes](/reference/rule-versions/#change-notes), which record how rules and skills changed, live in `changes/`. Projects never take them.
Library releases are Git tags, not files; see [Library releases](/reference/rule-versions/#library-releases).
Other supporting files, including `_README.md`, must live in an asset directory.
Rules and [rule group metadata](/reference/rule-format/#rule-group-metadata) must use valid paths; a prefix selector also rejects rules whose rule group metadata is missing.
The builder does not inspect the contents of rule groups a project doesn't include.

`config.yaml`, change notes, and rule group metadata use one YAML document per file. Duplicate keys, anchors, aliases, and explicit tags are rejected. The lockfile and generated data files remain JSON.

## The manifest

The `library` section of `.trailguide/config.yaml` is the library's **manifest**. It makes the repository a library, declares its [license](#license-metadata), and sets the [level](#skill-levels) of each skill it offers:

```yaml
schemaVersion: 2
sources:
  mattpocock:
    repository: https://github.com/mattpocock/skills.git
    ref: main
library:
  formatVersion: 1
  license:
    spdxExpression: MIT
    file: LICENSE.md
    notices: []
  skills:
    required: [skills/ship-service]
    recommended:
      - skills/build-feature
      - mattpocock:skills/engineering/to-spec
    offered:
      - mattpocock:skills/productivity/grilling
```

The rest of the file is an ordinary [configuration](/reference/configuration/): the library's own sources and what it takes from them, and its skill targets. Run `trailguide library init` to add a manifest to a repository; it writes `formatVersion: 1`.

### Library format

`library.formatVersion` is required. It names the version of everything the library publishes, which this page and [Rule and rule group format](/reference/rule-format/) describe:

- the `library` section: its format, license, and skill levels;
- the `repository` and `ref` of each source the library's skills [curate](#curated-skills) from;
- rule files and rule group metadata;
- the library layout: where the manifest, rules, skills, and shared assets live.

[Release records](/reference/rule-versions/#release-record) have their own `formatVersion`, which changes independently.

This version of Trail Guide reads and writes library format `1`. A library without `formatVersion`, or with one that isn't a whole number, fails with a validation error at `library.formatVersion`. A library in another format fails with `unsupported-library-format`, which names both formats: upgrade Trail Guide to read a newer one. Trail Guide doesn't promise to read every earlier format. It adds support for one when libraries still publish in it.

#### What a library's consumers read

A project that imports a library, and a catalog that lists it, reads only what the library publishes. It ignores the configuration's `schemaVersion` and every project setting, such as `skillTargets`, the sources the library doesn't curate from, and a curated source's own `rules` and `skills`, so a library in a project schema the consumer's Trail Guide doesn't know is still readable. It validates everything it reads, including each curated source's `repository` and `ref`. The project's [vendor snapshot](/reference/files/) keeps only that published manifest, and offline builds read it the same way.

Within a format, consumers ignore fields of the `library` section they don't know, at any level, so a later Trail Guide can add a field without a new format when ignoring it keeps every reader correct, such as a description. A change that consumers must interpret, such as a new skill level that projects must install, needs a new format, even if the new field is optional. `trailguide library check` is stricter: it validates the author's whole configuration, and fails on any field this version doesn't know.

#### What project configuration changes keep

Project configuration has its own [`schemaVersion`](/reference/configuration/#version-boundaries), which can change without a new library format, as long as it keeps what a library's consumers read:

- the manifest at `.trailguide/config.yaml`;
- one YAML document holding a mapping, without anchors, aliases, explicit tags, or duplicate keys;
- the `library` section, at the top level;
- under the top-level `sources` mapping, keyed by source name, the `repository` and `ref` of each curated source.

A change to any of these is a change to the library format.

The manifest replaces `rule-library.yaml`, and the Trail Guide directory replaces root-level `techs/`, `practices/`, `skills/`, `assets/`, and `changes/` folders. A repository with a `rule-library.yaml` fails to load with a message that shows the new shape; see [No backward compatibility](/reference/configuration/#no-backward-compatibility). Rule IDs don't change when you move a library's rules into `.trailguide/rules/`.

## Skills

Each folder in `skills/` is one skill, and its `SKILL.md` names it. `skills/` holds only skill folders, each directly inside it. Skills don't belong to rule groups, so a skill folder is never inside `rules/`, or inside another skill.

`trailguide library check` validates every skill, and a project installs only the skills it includes, its required skills, and the skills they call. A skill's version covers its whole folder; see [What a version covers](/reference/rule-versions/#what-a-version-covers). For the folder's contents, the `SKILL.md` fields, and every check, see [Skill format](/reference/skill-format/).

A skill can cite rules from any rule group in the library with `trailguide-rules-used`, and a project that installs it takes those rules too, for reference. Rules can't link to skills, and skills can't link to rules or other library files: a skill cites rules by ID, and its links stay inside its own folder.

### Skill levels

`library.skills` sets how strongly the library asks its projects to install each skill:

| Level | A project that uses the library installs the skill |
| --- | --- |
| `required` | Always, whatever it includes. It can't exclude or fork the skill, but it can rename it. |
| `recommended` | When it includes `recommended` or `"*"`, or names the skill. |
| `offered` | When it includes `"*"`, or names the skill. |

An authored skill that no list names, neither a level nor `dependencies`, is offered, so list only the skills you have an opinion about. Each skill can appear in one level, or in `dependencies`. Levels are library-wide settings: changing one needs no change note, and projects see the change, such as `recommended -> required`, in their update preview after the next library release.

A project sees only the levels of the libraries it names as sources. Levels don't chain: when your library curates a skill from another library, your projects see the level you set, not the other library's.

### Dependencies

List a skill in `library.skills.dependencies` when the library has it only because its other skills call it, and projects shouldn't install it on its own:

```yaml
library:
  formatVersion: 1
  skills:
    recommended: [skills/add-skill]
    dependencies: [anthropic:skills/skill-creator]
```

A project installs a dependency only with a skill that calls it, in its `trailguide-skills-used` or the project's `skills.uses`. `"*"` and `recommended` never include it, and a project that names it in `include` fails with a message naming the skills that call it. A dependency can be your own skill or one you curate. `trailguide library check` fails when nothing calls a dependency: none of your skills, and, for a curated one, no curated skill you list from its repository. See [Dependencies](/reference/configuration/#dependencies).

### Curated skills

A level, or `dependencies`, can list a skill from another repository as `<source>:<skill-id>`, where `<source>` is an entry in the library's own `sources`, with the `ref` the library tracks, such as `main` or a tag. A library curates skills only, and must list every skill it curates: a curated source's other skills don't reach projects.

Projects fetch a curated skill's files from the original repository, not from the library, and record which library required, recommended, or offered it. A library release doesn't lock a curated source's ref: each project resolves it when it runs `trailguide project update`, so moving a curated skill forward needs no new library release, and two projects on the same library release can hold different commits of it. A project overrides the ref by declaring the same repository as its own source. See [Curated skills](/reference/configuration/#curated-skills).

Your library repository is a project too, so it installs the required skills of the sources it curates from, as your projects do.

### Name clashes

Agents find skills by name, so `trailguide library check` fails when two skills the manifest lists, authored or curated, have the same name. It reads each curated source at its `ref` to find the names. Fix the clash in the library, so your projects never have to rename a skill to install both.

## Shared assets

Files that several rules use, such as a shared diagram, live in `.trailguide/assets/`. A rule's own supporting files live beside it instead. [Supporting assets](/reference/rule-format/#supporting-assets) covers both locations and the rules for linking to them.

Shared files are library-wide files: they aren't part of any rule or skill version, need no change note when they change, and reach projects with the next library release, when each project runs `trailguide project update`. See [What a version covers](/reference/rule-versions/#what-a-version-covers).

## License metadata

The optional `library.license` object declares the library-wide terms. Authors should use a `LICENSE.md` and optional `NOTICE.md` at the repository root; the manifest can identify other source locations:

| Field | Meaning |
| --- | --- |
| `library.license.spdxExpression` | Declared SPDX expression, such as `MIT` or `MIT OR Apache-2.0`, or a `LicenseRef-…` for custom terms. |
| `library.license.file` | Path to the actual license text, relative to the repository root. |
| `library.license.notices` | Paths to accompanying notices, relative to the repository root; use an empty array when none apply. |

When `license` is present, all three fields are required and all declared files must exist within the repository.
Declared license and notice files are [library-wide files](/reference/rule-versions/#what-a-version-covers), so they can't be part of a rule's or skill's version: a declared path can't be a rule's Markdown file, lie in a rule's asset directory, such as `.trailguide/rules/practices/testing/assets/verify-retry-limits/LICENSE`, or lie in a skill folder, such as `.trailguide/skills/build-feature/LICENSE`. Otherwise a later library release could replace a file that a project's pinned rule version covers. `trailguide library check` rejects such a declaration, and projects refuse to take a library release whose manifest has one.
A project's [vendor snapshot](/reference/files/) of the library stores a declared file from outside `.trailguide/` at its path from the repository root, beside the files from `.trailguide/`, so that path can't start with a name the snapshot uses for those files, or that Trail Guide 0.5 used for its records, in any letter case: `_source.json`, `config.yaml`, `assets/`, `curated/`, `changes/`, `rules/`, or `skills/`.
Unknown fields in the license declaration are rejected so misspellings cannot silently discard intended metadata.
Trail Guide retains the declared files from the resolved source commit and links generated rules to unchanged copies. Offline builds require those files in the stored snapshot.
If the declaration is absent, generated rules show no declared license. Trail Guide never infers an identifier from a filename. It validates supplied SPDX expressions and identifiers using its bundled license list, while allowing `LicenseRef-` identifiers for custom terms. This validates the declaration format, not ownership, permissions, or agreement between the declaration and the retained text.

Every library a project uses has a generated `libraries/<source-name>/README.md` with its repository, library release, requested `ref` or pins, each included rule's and installed skill's version and level and whether the project excludes or replaces it, or still includes it after the library retired it, a notice when it was taken from unreleased changes, declared SPDX expression when supplied, and links to retained terms and provenance. Libraries without a license declaration omit the `licenses/` directory. [Provenance](/reference/provenance/) documents the machine-readable records.

The manifest paths select **source files**, not output locations. For declared terms, Trail Guide uses these fixed destinations:

```text
generated/libraries/<source-name>/licenses/LICENSE.md
generated/libraries/<source-name>/licenses/notices/001.md
generated/libraries/<source-name>/licenses/notices/002.md
```

`<source-name>` is the name the project gave the source. Unique notice files are numbered in declaration order; repeated paths and a notice path identical to the license path are copied only once. No notice files are generated when none are declared. Contents, including whitespace and line endings, are preserved. Output paths are not configurable. Vendor snapshots retain the original names for traceability. Declared terms are retained even when exclusions or replacements leave no active rules from that library.

One library-wide license declaration covers every rule group, rule, and skill the library authors. A `license` or `licenses` field on a rule or rule group is rejected. A skill's `SKILL.md` can carry the Agent Skills `license` field, but it's informational: `trailguide library check` warns when it differs from the library's SPDX expression; see [Skill format](/reference/skill-format/#licenses). A curated skill keeps its own repository's terms, which Trail Guide finds as it does for any [non-library source](/reference/imports/#non-library-sources).
Keep original attribution with each rule and include required notices in the manifest. Material requiring a different declaration belongs in a separate library.
See [License rules](/guides/license-rules/) for publisher guidance and the boundary with the consuming project's license.

## Libraries in the earlier layout

Earlier versions of Trail Guide read a library's manifest from `rule-library.yaml`, and its groups, shared assets, and change notes from `techs/`, `practices/`, `assets/`, and `changes/` at the repository root. This version doesn't read that layout and doesn't move it. Every library command fails, writing nothing, while `rule-library.yaml`, `techs`, or `practices` exists at the repository root, with a message that shows where each file moves:

| Earlier layout | This layout |
| --- | --- |
| `rule-library.yaml` | The `library` section of `.trailguide/config.yaml` |
| `techs/<group>/`, `practices/<group>/` | `.trailguide/rules/techs/<group>/`, `.trailguide/rules/practices/<group>/` |
| `assets/` | `.trailguide/assets/` |
| `changes/` | `.trailguide/changes/` |

Move the files with `git mv`, then delete `rule-library.yaml` and write its `license` fields, without `formatVersion`, in the `library` section of `.trailguide/config.yaml`, beside the `sources` the repository uses as a project, if any. License and notice paths stay relative to the repository root, so they don't change.

Rule IDs and versions don't change. A moved rule sits two folders deeper, so its relative links to shared assets need one more `../`, such as `../../../assets/retry-lifecycle.svg`, and its links to license files at the repository root need two more. Links that start with `/assets/` still work, because a link that starts with `/` resolves from `.trailguide/`. Once the library has a library release, record each rule whose links changed with `trailguide library change RULE_ID --bump patch`, then run `trailguide library check`. A rule whose bytes didn't change needs no note, and moving the manifest isn't a library-wide change unless its license fields changed.

Projects can't import a library release in the earlier layout; sync and update fail with [`unsupported-library-layout`](/reference/imports/#source-limits-and-version-errors) until the library publishes a library release from the new layout and the project selects it. Rule versions that a library release in the earlier layout published still import when a later library release keeps them, unless one of their links resolves to another file in the new layout. A project that imported the library before it moved keeps a `vendor/<source-name>/rule-library.yaml`, which this version can't read either: once the library has published a library release from the new layout, delete `.trailguide/vendor/<source-name>/` and run `trailguide project sync`.

## Read libraries from other tools

Tools written in Go, such as a catalog of libraries, can read library release tags, release records, the library's manifest, rule files, rule group metadata, and the [canonical rule group list](/concepts/groups/#canonical-rule-group-ids), and place each library file in its repository, with the `github.com/fabricahq/trailguide/trailguide` package, whose Go documentation describes its API. Trail Guide reads libraries through the same package, so both read them the same way. The package only parses text the tool has already read, such as with a Git library; it has no Git, filesystem, or network access. Of a library's `.trailguide/config.yaml`, it reads only what the library publishes: the schema version, the names of its sources, and its library section, not the settings that configure the repository as a project. It follows Trail Guide's version, and its API may change before Trail Guide 1.0.0.
