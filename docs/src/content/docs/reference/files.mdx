Every repository that uses Trail Guide, whether a project, a library, or both, has the same **Trail Guide directory**, `.trailguide/` at its root. It holds the configuration, the rules, skills, and assets the repository authors, vendor snapshots of what it takes from each source, and generated guidance. When the repository installs skills, Trail Guide also writes them into **target folders** outside that directory, where agents look for skills.

`.claude/skills/` and `.agents/skills/` exist only for the [skill targets](/reference/configuration/#skill-targets) the repository configures, and only once it installs a skill. Your `AGENTS.md` stays outside the Trail Guide directory, at the repository root. Trail Guide maintains one section of it, between `<!-- trailguide:begin -->` and `<!-- trailguide:end -->` markers, and leaves the rest to you. A library also has `changes/` in its Trail Guide directory, for its [change notes](/reference/rule-versions/#change-notes); see [Library format](/reference/library-format/).

Initialize from the repository root. In Git repositories, other commands find the nearest Git root and use its `.trailguide/` directory. Outside Git, run commands from the repository root. See [Working directories](/reference/cli/#working-directories).

## Authored, vendored, and generated content

The Trail Guide directory holds three kinds of content:

- **Authored content: `rules/`, `skills/`, and `assets/`.** The rules, rule group metadata, skills, and shared assets written in this repository. Add your own rules and skills here, including replacements and forks of rules and skills you include from sources. You maintain these files; sync preserves them. A library publishes exactly this content.
- **Vendor snapshots: `vendor/<source-name>/`.** A copy of what the repository takes from each source, at the library release or commit that [`lock.json`](/reference/provenance/#inspect-the-lockfile) records for it, along with every rule's version and every file's digest. A library's snapshot mirrors its Trail Guide directory, with its `config.yaml` for the manifest, so a rule's relative links to the library's shared assets work in the copy too; license and notice files from outside the library's `.trailguide/` keep their paths from its repository root. A non-library source's files keep their paths in its repository. Skills a library [curates](/reference/configuration/#curated-skills) are stored with the library that listed them, under `curated/<curated-source>/`. Snapshots are kept per source because two sources can both have the same rule group ID. Do not customize them; put your changes in authored content instead.
- **Generated guidance: `generated/`.** The resolved rules your agents read. Trail Guide combines the included and authored rules according to `config.yaml`, applies exclusions and replacements, and writes the reading indexes, including `SKILLS.md`. Do not edit this directory; rebuild it after changing your inputs.

Installed skills are output too: Trail Guide writes a copy of each installed skill into every target folder, such as `.claude/skills/build-feature/`, from its vendored or authored source. See [Installed skills](#installed-skills).

Think of authored content and `vendor/` as inputs, and `generated/` and the installed skills as the output for your agents.
For example, when you replace a library rule, its vendored copy stays in `vendor/`, your replacement lives in `rules/`, and `generated/` presents the replacement to your agent.

## What to edit

| File or directory | Who maintains it | Purpose |
| --- | --- | --- |
| `AGENTS.md` | You, outside the Trail Guide section | Your instructions for agents. |
| The Trail Guide section of `AGENTS.md` | `trailguide project init`, `trailguide project build`, `trailguide project sync`, and `trailguide project update` | Tell your agent to read the generated rules and skills. |
| `.trailguide/config.yaml` | You | Choose sources, the rules and skills to include, versions, skill targets, exceptions, and, for a library, its manifest. |
| `.trailguide/rules/`, `skills/`, and `assets/` | You | Add authored rules, rule group metadata, replacements, skills, and shared assets. |
| `.trailguide/README.md` | `trailguide project init`, `trailguide project build`, and `trailguide project sync` | Explain the repository's rule setup and commands. |
| `.trailguide/lock.json` | `trailguide project sync` and `trailguide project update` | Record each source's revision, each rule's version, each installed skill, and every vendored file's digest. |
| `.trailguide/vendor/` | `trailguide project sync` and `trailguide project update` | Store vendor snapshots of the files `lock.json` records. |
| `.trailguide/generated/` | `trailguide project sync`, `trailguide project update`, and `trailguide project build` | Provide resolved rules, indexes, and the record of installed skills. |
| Skill folders that Trail Guide installed in `.claude/skills/` and `.agents/skills/` | `trailguide project sync`, `trailguide project update`, and `trailguide project build` | Provide installed copies of skills where agents look for them. |
| Other folders in `.claude/skills/` and `.agents/skills/` | You, or the tool that installed them | Trail Guide never changes or removes them. |

Keep your changes in configuration and authored content. Edits in `vendor/`, `generated/`, or an installed skill folder will be replaced or removed. To change a skill you include from a source, [fork it](/reference/cli/#fork-a-skill) into `skills/`.
Commit configuration, authored content, `lock.json`, both managed directories, and the installed skill folders, so your team, CI, and every fresh checkout use the same rules and skills offline.
Commit the project instructions and README as well.
If your `.gitignore` excludes a target folder, such as with `/.claude/`, change the line to `/.claude/*` and add the exception `!/.claude/skills/`, or `trailguide project check` reports the missing folders. Git can't re-include a folder inside an excluded folder, so `!/.claude/skills/` alone doesn't work after `/.claude/`.

Use `trailguide project build` to regenerate guidance from stored inputs, and `trailguide project check` to verify consistency without changing files.
Missing or mismatched vendor snapshots require `trailguide project sync`.
For recovery and file ownership details, see [Sync and recovery](/reference/sync/).

Generated Markdown and the managed Trail Guide guide include a "Generated by Trail Guide" notice and regeneration instructions. `generated/installed-skills.json` stores that notice in `generatedNotice`. Copied license and notice files retain their original bytes. An installed `SKILL.md` carries a [marker line](#installed-skills) instead, because its frontmatter must start at the first byte.

## Project and rule group guides

`trailguide project init` creates `.trailguide/README.md` with definitions and commands for managing rules. It preserves the repository's own `README.md` at the repository root.

After upgrading Trail Guide, run `trailguide project build` to refresh an older guide and regenerate guidance, or rerun `trailguide project init` to refresh only the guide and setup files. Build, sync, and init preserve valid configuration and authored content but refuse to overwrite a manually edited guide. Preserve those notes separately before refreshing it. `trailguide project check` reports a missing or outdated managed guide without changing it.

Managed guide format changes are breaking changes under the [version policy](https://github.com/fabricahq/trailguide/blob/main/.release-planner/policy.md#choosing-a-version): a new minor version of Trail Guide before 1.0, and a new major version after 1.0. This guide is separate from your repository's own README.

Creating a rule group also writes a `README.md` beside `_group.yaml`. Rule group guides explain how to add, edit, and validate rules. These are authoring documents, excluded from rule loading and generated guidance. Existing rule group files are preserved.

## Where agents start

The Trail Guide section of `AGENTS.md` points your agent to `.trailguide/generated/RULES.md`. It lists the rule groups and explains when to read each one.
Agents then open relevant rule groups and read the applicable rules in full.
When the repository installs skills, `RULES.md` also has one line pointing to `SKILLS.md`, so the same instructions reach agents whose tools don't load skills from the target folders.
See [Plan, write, and review](/for-agents/) for the section's text and a workflow built on it.

The commands that write the section create `AGENTS.md` when it's missing, and add the section after your text. Each refresh replaces only the lines between the markers. The begin marker records the Trail Guide version that wrote the section and a digest of its lines, so build, sync, update, and init refuse to replace a section edited by hand: move your text outside the markers and delete the section, then rerun the command. `trailguide project check` reports a missing or outdated section. To manage `AGENTS.md` yourself, set [`manageAgentsFile: false`](/reference/configuration/#agentsmd-section).

When `AGENTS.md` already points to `.trailguide/generated/RULES.md` outside the markers, as the section that earlier versions asked you to paste does, Trail Guide leaves the file alone and `trailguide project check` accepts it. To switch to the maintained section, delete your pasted section and run `trailguide project build`.

| Generated path | Contents |
| --- | --- |
| `RULES.md` | The entry point for discovering relevant rule groups. |
| `SKILLS.md` | One entry per installed skill. Present only when the repository includes skills. |
| `groups/` | Rule group pages containing full rules or summaries with links to full definitions. |
| `rules/` | Individual resolved rules, available even when a rule group also includes them inline, and the reference-only rules that installed skills cite. |
| `libraries/` | Source summaries and retained license and notice files. |
| `installed-skills.json` | The skill folders Trail Guide installed in the target folders. Present only when the repository includes skills. |

Large indexes can span multiple pages. Follow the page directory and navigation links before selecting rules, and complete any truncated reads.
Full rule definitions are never shortened to fit an index.

A rule's source name appears in its generated path. For example, `fabrica:practices/testing/test-failure-paths` lives at `rules/fabrica/practices/testing/test-failure-paths.md` under `generated/`.
Authored rules and replacements have no source name, so `practices/testing/test-failure-paths` lives at `rules/practices/testing/test-failure-paths.md`. Excluded rules and replaced rule bodies have no generated rule file.
A rule that only an installed skill cites has a generated rule file at the same kind of path, but no rule group page or `RULES.md` entry lists it.

For rule versions, replacement history, and retained license records, see [Provenance](/reference/provenance/).

## Installed skills

For each installed skill, Trail Guide writes the folder `<target>/<install-name>/` in every [skill target](/reference/configuration/#skill-targets), such as `.claude/skills/build-feature/`. The folder holds every file of the skill as its source has it, with each file's executable bit, plus two changes to `SKILL.md`, and a third when the repository [renames](/reference/configuration/#rename-a-skill) the skill: its `name` field becomes the install name.

First, a marker comment is the first line after the frontmatter:

```markdown
---
name: build-feature
description: Build a feature from an agreed spec, one slice at a time. Use when starting implementation of a new feature or a change to an existing one.
metadata:
  trailguide-skill-type: playbook
  trailguide-rules-used: |
    practices/testing/test-behavior-not-implementation
    practices/verification/verify-on-the-surface-users-touch
  trailguide-skills-used: |
    skills/tdd
---
<!-- trailguide:installed fabrica:skills/build-feature 1.3.0. Do not edit; fork it with trailguide project add skill --from. -->

1. Read the spec and name the slice you're building.
```

The marker names the skill's project ID and its version. A skill from a non-library source shows its full commit SHA in place of a version. An authored skill has no version, and its marker says where to edit it instead: `<!-- trailguide:installed skills/fix-bug. Do not edit; edit .trailguide/skills/fix-bug/ instead. -->`. A `SKILL.md` without frontmatter, which only a non-library source can supply, gets the marker as its first line. The marker never includes the Trail Guide version, so upgrading Trail Guide doesn't change installed copies.

Second, a generated section is appended to the end of `SKILL.md`. When the skill cites rules, it lists each one's project ID, version, and generated rule file:

```markdown
## Rules this skill applies

Read each rule in full before the step that applies it.

- `fabrica:practices/testing/test-behavior-not-implementation` 2.0.0: [.trailguide/generated/rules/fabrica/practices/testing/test-behavior-not-implementation.md](../../../.trailguide/generated/rules/fabrica/practices/testing/test-behavior-not-implementation.md)
- `practices/verification/verify-in-staging`, which replaces `fabrica:practices/verification/verify-on-the-surface-users-touch`: [.trailguide/generated/rules/practices/verification/verify-in-staging.md](../../../.trailguide/generated/rules/practices/verification/verify-in-staging.md)

Skills this skill uses: `tdd`
```

- A rule the repository replaced shows the replacement, its version when it has one, and the rule it replaces.
- A rule the repository excluded without a replacement shows "excluded by this project" and the exclusion's reason, with no link.
- The "Skills this skill uses" line names each skill it calls by its install name, including those your configuration's [`skills.uses`](/reference/configuration/#declare-the-skills-a-skill-calls) adds, and those an authored skill replaces. It appears only when the skill calls others, and without a heading when the skill cites no rules.

Links are relative to the installed `SKILL.md`, so they work from either target. A skill that cites no rules and calls no skills gets no generated section.

The copy in `.agents/skills/`, which Codex reads, can also get a generated `agents/openai.yaml` with the text Codex shows for the skill, from the [interface metadata](/reference/skill-format/#text-agents-show) in its `SKILL.md`. A skill that declares none of it gets no file, and a skill that ships its own `agents/openai.yaml` keeps it unchanged, in every target.

Trail Guide records what it installed in `generated/installed-skills.json`:

```json
{
  "formatVersion": 1,
  "generatedNotice": "Generated by Trail Guide. …",
  "skills": [
    {
      "name": "build-feature",
      "id": "fabrica:skills/build-feature",
      "version": "1.3.0",
      "commit": null,
      "targets": [
        ".agents/skills/build-feature",
        ".claude/skills/build-feature"
      ],
      "digest": "8c2f…d41a"
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `formatVersion` | The record's format version, `1`. |
| `name` | The install name, which is the installed folder's name. |
| `id` | The skill's project ID. |
| `version` | The installed version, or `null` for an authored skill, a skill from a non-library source, or one with unreleased changes. |
| `commit` | For a skill from a non-library source, including a curated one, the full commit SHA it came from; otherwise `null`. |
| `targets` | Each folder Trail Guide installed the skill in, relative to the repository root, sorted. When one target folder links to the other, both paths are listed, though the files are written once. Empty when the repository has no skill targets. |
| `digest` | The SHA-256 checksum of the installed folder: every file's path, executable bit, and contents, as sync wrote them. It leaves out a generated `agents/openai.yaml`, which only the `.agents/skills/` copy has. |

This record is how Trail Guide knows which folders it owns: it replaces and removes only the folders listed here, and refuses to write over any other. See [Who owns the target folders](/reference/sync/#who-owns-the-target-folders).

### SKILLS.md: find a skill

`generated/SKILLS.md` has one entry per installed skill, so people, and agents whose tools don't load skills from the target folders, can see what's installed, where it came from, and why:

```md
### build-feature

Build a feature from an agreed spec, one slice at a time. Use when starting implementation of a new feature or a change to an existing one.

- **Skill:** `fabrica:skills/build-feature`, version 1.3.0
- **Level:** recommended by `fabrica`, release 7
- **Type:** playbook
- **Installed at:** `.agents/skills/build-feature/SKILL.md`, `.claude/skills/build-feature/SKILL.md`
- **Applies:** 2 rules
- **Uses:** `tdd`
- **Installed because:** included
```

**Level** names the skill's [level](/reference/configuration/#skill-levels) and the library and library release that set it, such as `required by fabrica, release 7`. It's absent for an authored skill, and for one the repository named directly from a non-library source. A skill installed only because another one calls it says so, such as `**Installed because:** used by build-feature`. **Type** is absent for a skill without one, and **Uses** for a skill that calls none. A renamed skill's heading is its install name, and its entry adds `**Renamed from:** review-change`. A skill from a non-library source shows its commit in place of a version. With no skill targets, **Installed at** gives the skill's source folder in `vendor/` or `skills/` instead, and **Applies** lists the generated file of each rule it cites, because no installed copy carries that list.

`SKILLS.md` lists skills; it doesn't tell agents to prefer them over skills a person installed. See [Personal skills with the same name](/reference/sync/#personal-skills-with-the-same-name).

`RULES.md` points to this file with one line:

```md
This project also installs agent skills. See [SKILLS.md](SKILLS.md) for what each one does and where it's installed.
```

## Example: follow a rule from the index

These abbreviated excerpts show how an agent finds an authored rule. The full generated files also include reading instructions, metadata, and source information.

### RULES.md: choose a rule group

`.trailguide/generated/RULES.md` is the starting point. Each entry tells the agent when to open a rule group:

```md
### Testing

**When to read this group:** When adding or changing behavior, fixing bugs, or reviewing tests.

**Open group:** [Testing](groups/practices/testing.md)
```

### Rule group page: find the rules

`.trailguide/generated/groups/practices/testing.md` contains the rule group's rules. Small rule groups include full rule text; larger ones use summaries like this, linking to each full definition:

```md
### Test changed behavior

Rule ID: `practices/testing/test-changed-behavior`

**When to read:** When adding or changing externally visible behavior.

**Read full rule:** [Test changed behavior](../../rules/practices/testing/test-changed-behavior.md)
```

A rule from a source also shows its version below its ID, so agents and reviewers can cite it:

```md
Rule ID: `fabrica:practices/testing/verify-retry-limits`

Version: 1.3.0
```

Authored rules have no version.

### Rule file: read the guidance

`.trailguide/generated/rules/practices/testing/test-changed-behavior.md` contains the rule the agent follows:

```md
# Test changed behavior

Rule ID: `practices/testing/test-changed-behavior`

## Guidance

When a change alters behavior that a caller or user relies on, add or update a test for that outcome.
```

The authored version stays in `.trailguide/rules/practices/testing/test-changed-behavior.md`. Edit that source file and rebuild to update the generated copy.
